# Общий инженерный workflow

Scope: `jarvis/project/*` — инженерная работа зарегистрированного проекта. Для обслуживания кода personal/instance аналогичные технические приёмы применяются по документации компонента, без наследования правил какого-либо проекта.

## Цель

Скорость генерации кода не является критерием завершенности. Изменение считается готовым только тогда, когда понятны его архитектурное место, границы ответственности и фактические доказательства работоспособности.


## Перед изменениями

Codex должен:

1. Проверить `git status` в корне и в реально затронутом nested repository; не откатывать и не форматировать чужие изменения.
2. Определить минимальный scope задачи и не добавлять слои, abstractions или cleanup вне этого scope.
3. Назвать для себя:
   - entrypoint изменяемого поведения;
   - владельца состояния;
   - data-flow и side effects;
   - затрагиваемые публичные contracts;
   - затронутые приложения/packages и применимые требования версионирования;
   - применимые архитектурные правила;
   - проверки, которые могут доказать результат.
4. Если документация и код расходятся, сообщить об этом пользователю до архитектурного решения. Локальная узкая правка может продолжиться только когда она не закрепляет спорное отклонение.

## Во время реализации

- Делать одну смысловую вертикальную правку за раз и ограничивать объем непроверенного WIP.
- Переиспользовать существующие owners, modules, services, adapters, UI primitives и patterns, если они соответствуют каноническому стандарту.
- Не считать существующий legacy-паттерн разрешением копировать его.
- Сначала выражать invariant через types, encapsulation и публичный API; ESLint и существующие project scripts использовать для детерминированных границ, а смысловые границы прослеживать интеллектуально.
- Не создавать универсальный helper, config, registry или generic без текущей необходимости и хотя бы одного реального consumer.

## Проверка

Перед проверками прочитай [бюджеты и evidence](testing-and-benchmarks.md). Разрешения на тесты задаются владельцем и применимым профилем; при запрете запусков без запроса соблюдать его исключения для критически важных модулей. Не выдавать static inspection за runtime.

Проверки выбираются пропорционально риску и явным инструкциям пользователя:

- `diff` и `git diff --check` подтверждают только состав и механическую чистоту изменений;
- typecheck подтверждает статические TypeScript contracts, но не runtime behavior;
- lint подтверждает только включенные правила;
- unit/contract/integration tests подтверждают только покрытые сценарии;
- browser/live-domain проверка является отдельным доказательством;
- успешная локальная проверка не доказывает CI, deployment или production.

Если тесты не были запрошены и применимые правила их не требуют, Codex их не запускает. Незапущенные проверки всегда перечисляются явно; исходные failures отделяются от ошибок измененного scope.

При тестировании в браузере отдавай преимущество открытым вкладкам пользовательского браузера, а не headless-браузерам.


Audit/review по умолчанию read-only. Реализация, commit, push, tag, publish и deploy требуют соответствующего поручения; уже выданное разрешение сохраняется в своём scope. Порядок review и хранилище результатов задаёт проект.

## Отчет по завершении

Итог должен позволять быстро восстановить контекст без чтения всего diff:

- что изменилось в поведении;
- где entrypoint и source of truth;
- какие ключевые файлы затронуты;
- какие версии приложений/packages изменены и почему выбран этот уровень;
- какие invariants сохранены;
- какие проверки выполнены и что именно они доказывают;
- что не проверялось;
- какие риски или архитектурные расхождения остались.
- какие правила и skills были добавлены или актуализированы; явно запрошенные пользователем отдельные задачи укажи отдельно.

AI-review не заменяет ESLint, compiler, tests и runtime verification, а они не заменяют смысловую проверку ownership и data-flow. Для рискованных изменений полезен независимый review из чистого контекста.


Перед завершением классифицируй rule/skill impact: повторяющийся invariant относится к нормативному владельцу, повторяемый workflow — к навыку. Не создавай задачи-напоминания без просьбы пользователя.
