# Иерархия и нормативные документы

## Сборка эффективного профиля

Инструкции загружаются и объединяются в таком порядке:

1. общие инструкции Jarvis;
2. выбранная область: personal, instance или project;
3. применимые общие правила Root и выбранной цепочки групп;
4. явно подключённые common-документы направления и фактического стека;
5. common категории: application, package, service или другой тип;
6. документы конкретного проекта/target.

Уровни 3–6 подключаются только в project scope и только при наличии соответствующего владельца. Personal и instance не создают фиктивный project target.

Более узкое правило может уточнить, усилить или переопределить родительское только в своём target scope. Переопределение явно указывает:

- родительский rule ID;
- target и точный filesystem/runtime scope;
- заменяющий invariant или сужение;
- причину, почему common-вариант неверен для target;
- condition удаления, если override временный.

Без явного override побеждает родительское правило. Правила соседнего target не подключаются по одному факту соседства. Переиспользуемый common-документ другого владельца участвует только через явную ссылку маршрутизатора в пределах собственного Scope; он не подключает весь профиль владельца.


Области personal и instance не наследуют инженерные правила проекта. Соседние проекты и scopes читаются только как справка; их правила не становятся управляющими без явного common-маршрута. Разговор о компании или продукте поднимает относящиеся знания; обсуждение архитектуры и изменение кода дополнительно выбирают инженерный профиль. Один npm dependency или название папки не определяют стек, родителя и полный набор требований. Место хранения не определяет применимость.

### DOC-CONTEXT-001 — Эффективный профиль собирается от common к target

- Scope: `jarvis/*` — любая задача, затрагивающая нормативный target выбранной области Jarvis.
- Invariant: agent загружает все common-уровни маршрута и target-specific документы, применяя только явные scoped overrides.
- Запрещено: заменять common-правило на основании кода, README соседнего target или неявного precedent.
- Evidence: `architecture-review`, маршрут документов и ссылки override.


## Типы документов

- `architecture` — ownership, layers и направление зависимостей;
- `contract` — точный API, data format, lifecycle и compatibility;
- `standard` — обязательное правило процесса;
- `workflow` — регулярный процесс выполнения задачи;
- `skill` — переиспользуемый workflow Codex с точным trigger и границами внешних действий;
- `runbook` — пошаговая operational-инструкция;
- `reference` — описание текущей реализации, не переопределяющее architecture;
- `task`, `roadmap`, `research` — ненормативный материал до переноса принятого invariant.


### GOVERNANCE-CURRENT-001 — Governance описывает только действующий контракт

- Scope: `jarvis/*` — нормативные architecture, contract, standard, workflow и reference документы.
- Invariant: документ формулирует актуальное устройство и правила проверки текущего кода без привязки к номеру релиза, завершённой миграции или прежнему состоянию реализации.
- Safe path: после изменения контракта нормативный текст заменяется актуальной формулировкой; причины и хронология остаются в Git history, release notes или внешнем task-tracker.
- Запрещено: разделы вида «начиная с версии N», завершённые migration guides, таблицы «до/после» и closed backlog внутри нормативного профиля.
- Evidence: `hard-static` по содержимому governance и `architecture-review` на соответствие текущему коду.


Профильные архитектурные правила имеют одного владельца; каталог и локальная проекция лишь ссылаются на него. Текущий код и нормативный текст сопоставляются; расхождение сообщается до его распространения. История, исследования и планы сами по себе не становятся правилами. Новый раздел создаётся при реальном нормативном содержании или задаче маршрутизации.
