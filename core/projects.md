# Проекты, группы и размещение знаний

## JARVIS-PROJECTS-001 — Единый каталог

- Scope: все экземпляры Jarvis с модулем `projects`.
- Invariant: `projects/<id>/project.json` schema 2 — единственный владелец идентичности, типа, родителя и адресов; `project.md` — краткое назначение и навигация. Физический каталог плоский. `kind: project|group` меняет только отображение; состав материалов и поведение одинаковы. ID неизменяем, название изменяемо; один родитель, циклы запрещены. Проект может не иметь исходников и рабочей папки. Группа может быть внутри проекта, проект внутри группы или проекта.
- Стандартные разделы: `rules`, `skills`, `specs`, `test-specs`, `notes`, `assets`, `reports`, `software`. Создавать каталог только при наличии содержимого. Пустая папка не является свидетельством реализации.
- Evidence: `bootstrap/scripts/projects.py --root ROOT validate`, корректная цепочка родителей и разрешение адресов.

## JARVIS-STORAGE-001 — Один действующий источник раздела

- Scope: карточки schema 2 и все операции с их материалами.
- Invariant: `storage.default: {root, path}` задаёт основное место; `storage.sections[section]` — необязательное исключение. Без исключения адрес равен default/path + имени раздела. `root: jarvis` обозначает экземпляр, остальные root IDs разрешаются через `config/project-roots.json`. Все `path` относительны корню; переход за границы через `..` или symlink запрещён. Внешний root существует до записи, `root.json` пользователю не создаётся.
- Отсутствующая папка раздела создаётся по назначенному адресу. Недоступный root означает ошибку привязки: не создавать root, не выбирать другое хранилище и не писать глобальную замену. При отсутствии назначения у legacy-проекта сначала согласовать storage; legacy-записи не превращаются в schema 2 молча.
- `repair` ищет только известные адреса, соседей прежнего пути и переданные кандидаты. Агент сопоставляет структуру, документы и доступные Git/другие признаки. Название, remote или одинаковый commit не доказывают уникальность checkout. При неоднозначности — вопрос с кандидатами. Перепривязку подтверждает пользователь либо однозначное проверенное свидетельство; прежние адреса сохраняются.
- Перенос: показать source/destination, проверить назначения, скопировать, сравнить hashes и неизменность источника, переключить карточку, исправить входящие ссылки, удалить прежний источник. CLI хранит журнал и сохраняет source до `finalize-transfer`; после сбоя агент продолжает по журналу, не объявляет две копии действующими. Значимые данные не считать cache по имени папки.
- Символические ссылки являются производной навигацией, не второй базой адресов. Изменять карточку до/вместе с их обновлением.

## JARVIS-PROFILE-001 — Область работы и наследование

- Scope: все задачи над зарегистрированными проектами.
- Invariant: определить проект по текущему поручению и `sources`, а не только cwd. При нескольких подходящих привязках учитывать задачу и спросить, если выбор меняет полномочия или правила. Загрузить общий `core`, затем собственные правила предков от корня к выбранной записи. `rules_entry` по умолчанию `README.md`; маршрутизатор может подключать явно применимые common-документы. Не загружать все дочерние и соседние ветки. Root — логическая группа рабочих направлений; она не тождественна монорепозиторию или продуктовой группе Endge. Иерархия знаний, sources и storage независимы. Frontend, Backend и Deployment оформляются применимыми разделами правил группы, точный стек — документами проекта. Общие документы другого владельца становятся обязательными только по явному common-маршруту с сохранением собственного Scope; это не наследование соседней ветки.
- Уточнение не отменяет родительский запрет. Override обязан назвать rule ID, точную область, заменяемое требование и основание. Разрешения среды и пользователя сохраняют приоритет. Родство и место хранения не дают права менять соседние проекты. Читать относящиеся материалы другого проекта как reference допустимо в доступах задачи; это не подключает всю чужую ветку. Явно выбранный common-документ другого владельца применяется только по маршруту и в пределах собственного Scope.
- Иерархия карточек — владелец структуры; порталы и БД хранят только проверяемые проекции, сохраняя исторические scope IDs и ссылки review/audit. Общие процессы проекта не превращать в глобальные требования всем пользователям.

## JARVIS-PROJECT-MEMORY-001 — Память совместной работы

- Scope: общение с владельцем в project/group и `memory_mode=auto`.
- Invariant: общающийся агент сам сохраняет значимые пожелания, уточнения, решения, отклонения, утверждения конкретных планов, результаты и незакрытые вопросы в `notes` выбранной записи. Не ждать «запомни», завершения чата, расписания или фонового агента. Сначала прочитать актуальную заметку и проверить дубликаты; собственную гипотезу не приписывать пользователю.
- `notes/README.md` — указатель тем; `working-context.md` — краткое текущее состояние, открытое, следующий шаг; `preferences.md` — пожелания в этом проекте; `decisions.md` — существенные утверждения/отмены; `topics/` — подробности разросшихся тем. Создавать только необходимые файлы. Одно знание имеет одного владельца, обзоры ссылаются на него. Сведения обо всех проектах пользователя принадлежат personal, общие решения группы — группе.
- `notes/discussions/` — датированные рабочие обсуждения, его README — хронологический указатель; источники и вложения находятся в `assets/discussions/` того же владельца. Общая конвенция для любой группы/проекта — [core/discussions.md](discussions.md). Она не вводит новый стандартный раздел карточки и не делает протокол нормативным правилом.
- Существенная запись содержит дату, источник и статус: пожелание, предложение, утверждено, отклонено, открыто или выполнено. Разделять согласование внешнего вида, камеры, механик и фактической реализации. Хранить причины решений. Принятый technical contract становится spec со ссылкой из заметки. Открытые вопросы не исчезают при смене темы.
- Перед продолжением читать project.md и working-context, затем релевантные темы. Исходные фрагменты сохранять при обоснованной необходимости по core/memory.md с честными границами покрытия; не обещать полноту по одной сводке. Эта файловая память не является встроенной памятью клиента.

## JARVIS-SOFTWARE-001 — ПО и его данные

- Scope: ПО уровня instance, project или group.
- Invariant: общий владелец использует `software/<id>`, проект/группа — свой раздел `software`. В папке `software.json` и README; необязательные компоненты `source`, `install`, `data`, `runtime`. Установленное ПО можно зарегистрировать по внешнему адресу без копирования. Разработанное ПО может храниться внутри или по привязке. Одна программа имеет одного владельца, остальные используют ссылки.
- `data` — значимые данные, `runtime` — временное состояние. БД задач, история и единственные материалы не являются cache. Skills описывают workflow, software содержит/адресует исполняемое ПО. Регистрация сама по себе не устанавливает и не запускает программу. Общий экземпляр не означает общие права доступа.

## Управление и предложения

Использовать `modules/projects/SKILL.md`. Создание требует поручения; если агент заметил самостоятельную длительную цель, предлагает проект/подпроект с родителем и рекомендацией размещения. Не регистрировать каждую реплику или каталог. При отказе не повторять предложение без изменения контекста.

Если пользователь не назвал storage, предложить «всё в Jarvis», «всё локально» или смешанный вариант с учётом существующих материалов, явных предпочтений и подтверждённых прошлых выборов. Рекомендация не заменяет ответ. Не выдумывать статистику. Названные пользователем назначения не переспрашивать. Полный каталог и личные сведения не загружать ради одной проектной задачи.

Переименование сохраняет ID. Переназначение родителя показывает изменение цепочки правил и явно подключаемых common-документов. До переключения сверить прежние применимые требования с новым маршрутом; не расширять Scope из-за нового родителя или места хранения. При split/merge нормативные блоки сохраняют ID, условия и evidence; старые адреса и используемые якоря остаются ненормативными переходами к единственному оригиналу. CLI rules показывает только родительские entrypoints, validate проверяет структуру: эти результаты не доказывают полноту эффективного профиля. Архивирование с активными детьми требует сначала согласовать их судьбу. Постоянное удаление — только явное поручение, с проверкой детей, ссылок и данных; CLI сохраняет recovery copy и честно не обещает стирания Git/архивов. Нельзя повторно использовать удалённый ID.
